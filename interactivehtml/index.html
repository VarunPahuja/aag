Autonomy that is earned, not granted.

Adaptive AI Governance Platform — Earned Autonomy Engine

An enterprise deploys an AI agent to approve invoices. Someone sets its spending limit on day one, and nobody revisits it. We make that limit a variable — continuously repriced by statistical evidence from the agent's own decision history, raised only with human sign-off, and clawed back automatically when performance degrades.

Context

What the manual process looks like today

Invoice approval runs on a delegation of authority matrix. Every approver carries a spending limit tied to their role — team lead, manager, director, finance. An invoice arrives, gets matched against its PO, and routes to whoever's limit covers it.

That limit is set by policy. It changes on promotion, or at the annual DOA review. It does not change because a particular approver has been accurate for eight months.

The controls around it are periodic and retrospective. Internal audit samples a batch of approvals each quarter. Exceptions surface at close, or when a vendor complains, or when a payment reverses. Errors are caught — weeks or months later.

What happens when an AI agent enters that process

Nothing about the matrix changes. The agent is slotted in as another approver with a fixed limit, set low because nobody is sure. And it stays there, because the DOA review is about roles, not performance.

Proven agents stay capped

Humans keep reviewing decisions the agent has demonstrably mastered. The ROI that justified the deployment never arrives.

Degrading agents keep privilege

A drop in quality is invisible until the next quarterly audit sample happens to catch it. The detection window is a quarter wide.

What we change

Three things, all of which map onto controls that already exist rather than replacing them.

Control todayHow it works nowUnder our platform
Delegation of authorityA constant, set by role, reviewed annuallyA variable, repriced by evidence, still human-authorised
Internal audit samplingA batch pulled quarterly at fixed costContinuous, at a rate that falls as trust is proven
Degradation detectionNext audit cycle — up to a quarterWithin one review window, with automatic clawback

What deliberately does not change: a human still authorises every increase, exactly as they would a DOA amendment, and every change is logged against a named approver.

Mechanism

The control loop

One invoice, start to finish. Note where the LLM sits: there is deterministic code on both sides of it.

Two return paths, deliberately asymmetric. The slow path on the left requires a human signature before a limit rises. The fast path on the right drops the limit the moment drift is confirmed or a critical error appears — no human needed. Removing authority is always the safe direction; granting it is not.

Architecture

Four kinds of authority, four components

The rule the whole system is built around. Each component does exactly one of these jobs, and none of them can do another's.

LLM reasons
Reads evidence, writes explanations. Never originates a verdict.
Statistics provide evidence
Pure arithmetic over the decision log. Reproducible by anyone.
Policy engine enforces
The only code that changes or blocks anything. Deterministic.
Humans authorize
Required before autonomy rises. Not required to take it away.

Trust & risk engineUtkarsh · trust/

Pure statistics over the decision history — no database, no network, no clock. Wilson confidence bounds on accuracy, human agreement and utilization; critical-error weighting; two-stage drift detection; a composed trust score; and the ladder decision with cooldowns and clawback. Deterministic by contract, so any number it produces can be recomputed and defended.

Agentic governanceVarun C. · governance/

Four LangGraph agents — Risk, Performance, Compliance, Audit — each writing an independent opinion on the evidence, combined by a coordinator into one recommendation an administrator can read. Disagreement between agents is surfaced, not averaged away. They produce recommendations only: no database writes, no policy mutation, enforced by a CI check on imports.

One LLMClient protocol sits behind all three providers — Gemini, Claude and OpenAI — selected per agent by configuration, not hard-coded. The demo itself runs on recorded responses, so LLM latency and availability sit outside the demo path entirely. Provider independence turned out to be a practical constraint, not a theoretical nicety: Gemini's free tier is 20 requests per day, not per minute, which makes a single-provider dependency a real risk to a live demo rather than an edge case.

Backend & policy infrastructureVarun P. · backend/

The policy engine — the only component that enforces a limit, and a pure module with no LLM, database or network inside it. Plus the hard ceiling that clamps governance recommendations to what the evidence supports, immutable policy versioning, the hash-chained audit log, the approval workflow, JWT and role-based access, and the API surface every other lane meets at.

Product, simulation & observabilityAdhya · frontend/ simulator/

The dashboard an administrator actually uses — trust over time, ladder position, drift status, approvals queue, audit trail. And the simulator that generates synthetic invoices with known ground truth, so twelve weeks of agent behaviour compresses into a few minutes and the demo is reproducible from a seed.

The core idea

Why accuracy alone is not evidence

An agent that is five-for-five looks perfect and tells you almost nothing. We do not score on the raw rate — we score on the lower bound of a Wilson score confidence interval, which accounts for how much we have actually seen.

Move the sample size and watch the bound

Point estimate
100.0%
Wilson lower bound
56.6%
evidence floor

The consequence: a perfect five-for-five record scores worse than 384-of-400. The bound rewards being good and having proven it. That is what makes the autonomy earned rather than granted, and it is why an increase requires evidence to accumulate rather than a lucky streak.

What else feeds the trust score

Human agreement

When the agent escalates, does the human reach the same conclusion it would have? Measured only on ruled escalations, with its own evidence gate.

Critical-error weighting

Approving what should have been rejected sends money out. The reverse annoys a vendor. Weighted 5× in the score — never folded into accuracy itself.

Drift detection

A 10pp accuracy-drop tripwire, then a pooled two-proportion z-test to confirm. Below 30 samples per window we report "underpowered" rather than claiming certainty.

Where ground truth comes from

In production nobody re-checks an invoice the agent auto-approved, so accuracy has no natural source. We added post-hoc audit sampling: a share of autonomous approvals goes to human review after the fact — 100% at the floor rung, 5% at the top. That sampled review is the ground truth, and the falling sampling rate is the measurable return: not just fewer escalations, a shrinking oversight burden.

Research

What already exists, and the gap we sit in

Before writing another line of code we ran a prior-art review: does this already exist? Graduated agent autonomy turns out to be a crowded, now-commercial idea. Unit21 sells a "progressive autonomy trust ladder" for compliance queues, structured L0–L3, matching our rung design; Monte Carlo Data markets agentic autonomy explicitly as a trust score; even Anthropic's own claude-code repository carries an open feature request for a similar "ask before acting → act and report → full autonomy" ladder. None of that is ours to claim — the ladder is a correct implementation of an established pattern, not an invention.

The closest software prior art overlaps us on pieces of the shape — a governance layer, human-in-the-loop approval, risk-graded actions — but none of it raises or lowers an authority limit on the basis of measured accuracy. That gap is the project.

Closest prior artOverlaps with us onRepriced by measured accuracy
evidence-gate/agentgovGovernance layer, human-in-the-loop approval, risk-graded action classification, approval-queue dashboardNo — rule-based; by its own docs, "each rule, no LLM-based guardrails"
VERITAS OSDecision control, policy enforcement, audit trails, replayable evidenceNo — runtime enforcement only, no earned-autonomy mechanism
HumanLayerApproval gates and escalation paths wrapped around tool callsNo — human-in-the-loop plumbing only, no trust model
Microsoft Agent Governance Toolkit (MIT, Apr 2026)Open-source runtime security for agentsNo — security posture, not autonomy calibration
This projectSame shape: a governance layer beside the decision path, human-in-the-loop approval, risk-graded actionsYes — a Wilson lower bound on measured accuracy gates the ladder

The Wilson bound itself is not new — it is established for scoring small samples fairly in product ratings and comment ranking, and at least one USPTO patent applies it for the same reason we do — but no instance of it gating agent permissions turned up in the search. The one paper that overlaps us technically, Governing What You Cannot Observe (Marín & Chaudhary, University of Turku, arXiv:2604.24686, April 2026 — the "RiskGate" system), shares our drift-detection and adaptive-threshold math and then argues directly against putting an LLM anywhere in a governance loop: "LLM-based evaluators introduce latency, cost, and the recursive problem of governing the governor." That objection lands on systems where the LLM is the governor; ours never is — statistics compute the evidence, deterministic code enforces it, and a human authorizes every increase, with the LLM writing only the rationale a reviewer needs to sign off. RiskGate also runs with no human in its authorization loop at all and no empirical evaluation of its own; this project has both.

Honest limitation. This review found no duplicate of the specific construction — Wilson-bound gating of a ladder, argued over by a non-authoritative multi-agent panel, with asymmetric clawback — but the nearest neighbors are a research paper with no running system and open-source tools that solve adjacent problems, not shipped products at feature parity. This remains a prototype demonstrating a mechanism in one decision category with a simulated decision stream.

Deliberately excluded

Celery, Redis, Prometheus, Grafana, OpenTelemetry, Jaeger, MLflow, object storage and Kubernetes were all scoped out, each recorded as an architecture decision. The system is a monolith with enforced module boundaries — the boundaries that matter here are architectural, not network, and we enforce them with import rules in CI rather than paying for a distributed system on a three-week build.

Headless by design

The backend's only public surface is a committed OpenAPI schema, with a CI check that fails the build the moment the schema goes stale against the code that generates it. The frontend and the simulator are pure HTTP clients against that schema — neither imports backend code or touches the database directly. Frontend types are meant to be generated from it rather than hand-written, with the same staleness discipline extended to catch a hand-edit once that migration lands. It is the same boundary discipline that keeps the trust engine and the policy engine from reaching for a database, applied one level up to the platform's own internal seam.

How correctness is defended

Statistics cross-validated

The Wilson implementation is checked against statsmodels as an independent reference, plus property-based tests over random inputs.

Boundaries enforced in CI

Tests fail the build if the trust engine imports a web framework or database, or if governance can reach the enforcement path.

Adoption

What onboarding an agent looks like

The integration surface is a single HTTP call. An existing agent adds one request before it acts and receives a verdict — no change to the agent's internals, no rewrite, no framework dependency.

Register the agent

An administrator creates the agent record and names its decision category. Takes minutes; it is a form, not an integration.

Set the floor and the ladder

The agent starts in probation at the floor rung — ₹500 — with 100% of its autonomous approvals sampled for post-hoc review. Business owners define the stake bands; this is the workshop step, and the one that needs real subject-matter input.

Add one call to the agent

POST /api/v1/decisions before it acts. Within limit, it proceeds and the decision is logged. Outside limit, it escalates into the approvals queue the organisation already uses. Nothing else about the agent changes.

Evidence accumulates

Every decision, every human ruling on an escalation, and every sampled review feeds the trust profile. Nothing moves yet — the agent is building a record.

First recommendation

Once the sample size, trust threshold, cooldown, drift and recovery gates all pass, the governance agents produce a recommendation with reasoning. It appears in the approvals queue with the evidence attached.

An administrator signs

Approve or reject, with a written reason. A new immutable policy version is created, the ceiling moves one rung, and the sampling rate steps down. Every subsequent decision references that policy version.

Steady state

The agent climbs as it proves itself and drops automatically if it degrades. The administrator's involvement is one signature per rung change — not one per invoice.

Fail-closed by design. If the governance layer is unavailable, no recommendations are generated and the ceiling simply stops moving. If the policy engine is unreachable, every decision escalates. Autonomy is never silently granted by a failure.

Guidance requested

Where we would value your view

Ordered by how much the answer would change what we build in the remaining time.

Is post-hoc sampled review how ground truth is actually established?
Our answer to "how do you know an auto-approved invoice was correct" is sampling a share for human review after the fact, at a rate that falls as trust rises. Does that match how audit and controls functions genuinely work, or is there a mechanism we are missing — downstream signals like payment reversals, dispute rates, something in the close process?
Would a risk function accept statistical evidence as the basis for granting autonomy?
Or does the decision have to be rule-based, with statistics only as supporting evidence? This is fundamental to whether the concept is sellable, and we would rather know now than at submission.
Is invoice approval the right demo domain?
We chose it because ground truth is cheap to simulate. Is there a domain closer to how Deloitte engages — expense audit, contract review, KYC, claims — where this would land better with a panel? The loop is domain-agnostic; only the taxonomy changes.
Per-increase approval, or periodic review?
We require a human signature on every rung change. In practice, is autonomy reviewed decision by decision, or in batch — a quarterly access review, a monthly control forum? If it is batch, our approval workflow should reflect that.
One decision category in the demo, or two?
The original proposal argued per-category trust profiles and we scoped to one. The trust engine is a pure function over a decision list, so partitioning is a grouping change rather than an architectural one. Is two categories climbing at different rates a materially stronger demo, or does one clean narrative land better?
Is a fully open-source stack a strength or a gap?
Nothing here carries a licence cost. Does a client-facing audience read that as pragmatic and portable, or would they expect enterprise-grade components in the picture?
Should we build an integration adapter at all?
The proposal promised LangChain, RPA and REST adapters. We scoped to a single endpoint, with the simulator serving as proof of the middleware pattern — it is a fully external HTTP client that never imports backend code. Is one working adapter worth the remaining time, or is the endpoint plus the architecture argument sufficient?
Is there a Deloitte point of view we should align vocabulary with?
We would rather map to existing framework language than invent terminology that already exists. Return-on-Autonomy came from the brief — what else should we be aligning to?

Review notes

A compressed statement of what this project claims, so a reaction can be recorded against specific items rather than against the whole. Notes save in this browser and copy out in one action.

The project in eight claims

  1. Static permission ceilings, not model capability, are the binding constraint on agentic ROI.
  2. A ceiling should be a variable repriced by evidence, not a constant set by role.
  3. The evidence must be statistical and reproducible, never an LLM's judgement.
  4. Sample size matters as much as accuracy — hence the Wilson lower bound rather than the raw rate.
  5. Enforcement must be deterministic code the LLM cannot reach.
  6. Increases require human authorisation; clawbacks do not. Asymmetric risk, asymmetric controls.
  7. Ground truth in production comes from post-hoc sampled review, at a rate that falls as trust rises.
  8. The existing governance market observes and documents. None of it reprices the permission itself.

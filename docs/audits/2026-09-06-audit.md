### 1a/1b — the 500, reproduced, with a verbatim traceback

Postgres was already up and seeded (`aagp-db`, 3 agents). The backend was
started from the `origin/main` worktree exactly as specified — **no
`--reload`** — against the real `DATABASE_URL`:

```
cd backend && uvicorn app.main:app --port 8011
```

A concurrent load script (`httpx.AsyncClient` + `asyncio.gather`, semaphore-
bounded) fired valid `POST /decisions` bodies at three real seeded agents.

**At 40 concurrent in-flight requests, 1500 total calls: 746 failed with 500
(49.7%), 482 more failed as client-side connection resets, only 272
succeeded.** At a much gentler 5 concurrent: 124/600 failed (20.7%). At the
gentlest concurrency tested, 2 concurrent: **46/600 failed (7.7%)**.

**None of these numbers are close to "1 in 150-200" (0.5-0.7%).** The claim
that the bug exists is correct; the claim about its rarity is not. This is
not a rare edge case — it is the default outcome of any two decisions for
the same agent landing close together in time, and it gets sharply worse as
concurrency rises. (One caveat in the other direction: if a client submits
decisions one at a time, strictly sequentially, awaiting each response
before sending the next — which is how a naive simulator client would behave
today — the race window may rarely open at all. The claimed 1-in-150-200
figure may reflect exactly that kind of near-sequential client. Under any
real concurrency, the true rate is roughly two orders of magnitude worse than
claimed.)

row/agent differ):

**Root cause, confirmed precisely from this traceback**: `backend/app/api/v1/decisions.py:130-134`

```python
next_sequence = (
    db.execute(
        select(func.max(Decision.sequence)).where(Decision.agent_id == agent.id)
    ).scalar()
    or 0
) + 1
```

is a classic read-then-write race with no locking (`SELECT ... FOR UPDATE`
would fix it), no DB-generated sequence, and — because `decisions.py:180-192`
wraps the whole handler in nothing but the default FastAPI/Starlette
exception handling — **no `try/except` anywhere catches the resulting
`IntegrityError`**. Two concurrent requests for the same agent computing the
same `next_sequence` will always have one raise on insert. The exception
does not surface at the `db.add(decision)` line, because SQLAlchemy defers
the flush — it surfaces one call later, inside `append_entry` at
`audit_log.py:61`, whose own unrelated `SELECT` triggers session autoflush,
which is where the pending `INSERT` actually executes and fails. **This is
exactly claim (b)'s first half, confirmed to the line.** `append_entry`
itself is not the bug here; it's an innocent bystander that happens to be
the next statement that triggers a flush.

**The second half of claim (b) is also real, but doesn't cause this
crash — it causes something worse and quieter.** `audit_log.py:29-77`'s
`AuditLogEntry.hash` is the only column with a `unique=True` constraint;
`prev_hash` has none. Two concurrent callers of `append_entry` can both read
the same "latest" row (`audit_log.py:60-61`,
`order_by(AuditLogEntry.ts.desc())...first()`) before either commits, and
because their payloads differ, their computed `hash`es differ too — so
**neither insert conflicts, and both commit successfully with the same
`prev_hash`.** Checked directly against the live database after this load
test:

```sql
select prev_hash, count(*) from audit_log group by prev_hash having count(*) > 1;
-- 98 distinct prev_hash values, each shared by 2-3 rows
```

**The audit log's hash chain has silently forked into a tree in 98 places.**
`GET /audit-log`'s `verify_chain` (called every request) only recomputes each
row's own `hash` from its own `prev_hash` + payload — it never checks that
`prev_hash` values are unique, so it reports `chain_valid: true` on a
structure that is provably not a single linear chain. **This is a real,
separate, and arguably more serious bug than the crash** — it silently
undermines the one property ("immutable, hash-chained, tamper-evident") the
product is built to demonstrate, and it produces no error, no log line,
nothing a human would notice without querying `prev_hash` cardinality
directly, which is what this audit did to find it.

**The sequence of manual steps a human operator needs today, in order,
to walk this arc live:**

1. Bring up Postgres, migrate, seed (or use an already-seeded instance).
2. Start the backend without `--reload`.
3. Submit decisions **one at a time, sequentially** (not concurrently — real
   concurrency reproduces §1a within seconds). There is no retry logic in the
   real ingest path or in the simulator's own client for the sequence-race
   500 — a failed submission is simply lost.
4. To generate a recommendation, **manually call**
   `POST /agents/{id}/recommendations` — nothing in the backend calls this
   automatically on any schedule or event. This is true for every beat that
   needs a fresh evaluation, including the drift/clawback beats.
5. To show a live-earned INCREASE being approved, there is no way to do this
   honestly today without seed data — either use the two pre-seeded
   recommendations, or be prepared to show and explain the dissent/HOLD
   outcome as the actual system behavior (which is, unintentionally, a
   fairly compelling demonstration of the governance panel doing its job —
   just not the "agent earns more autonomy" story the beat is supposed to
   tell).
6. To show a clawback, inject critical-error decisions, call the
   recommendations endpoint, then **manually approve it** — same call, same
   step as an increase, despite the product's stated design.
7. The offline `simulator arc` command (PR #30, unmerged) sidesteps all of
   this — it runs the whole ten-beat story in-memory, with no backend, no
   database, and no network, and is genuinely deterministic and safe.
